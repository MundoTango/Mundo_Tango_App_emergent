1.1 PLATFORM PURPOSE
────────────────────────────────────────────────────────────────────────────
Mundo Tango is a comprehensive social platform for the global tango community,
built on the ESA (Emergent Software Architecture) LIFE CEO framework.

Key Objectives:
✓ Social networking for tango dancers worldwide
✓ Event management and discovery
✓ Community building (groups, profiles, connections)
✓ AI-powered life management through Mr Blue assistant
✓ Autonomous coding and platform customization
✓ Progressive user journeys (J1-J5 system)
✓ Enterprise-grade security and scalability

Target Users:
- Tango dancers (beginner to professional)
- Instructors and performers
- Event organizers
- Community leaders
- Platform administrators


1.2 CORE ARCHITECTURE PRINCIPLES
────────────────────────────────────────────────────────────────────────────
Architecture Pattern: Full-Stack TypeScript Monorepo
Development Methodology: MB.MD (Mapping→Breakdown→Mitigation→Deployment)
Deployment Strategy: Staged Rollout (Phase 1→2→3)

Six Non-Negotiable Rules (ALL AGENTS MUST FOLLOW):
1. VERIFY BEFORE BUILD - Read all docs, summarize requirements first
2. INTEGRATE IMMEDIATELY - Import components as you build them
3. SCREENSHOT EVERYTHING - Visual proof required for all UI changes
4. TEST USER JOURNEY - Test as regular user AND super admin
5. ARCHITECT VALIDATES - Independent review mandatory
6. CONTROLLED ROLLOUT - Phase 1 (super admin) → Phase 2 (10% beta) → Phase 3 (100%)

Primary User Profile:
- Technical Level: Non-engineer
- Interface: UI only (no logs/terminal access)
- Required Proof: Screenshots + Playwright tests
- Forbidden Claims: "Logs show working" without UI evidence


1.3 SYSTEM ARCHITECTURE LAYERS
────────────────────────────────────────────────────────────────────────────
Layer 1: Frontend (React + TypeScript + Vite)
  ├─ Client-side rendering
  ├─ Component-based architecture
  ├─ React Query for data fetching
  ├─ Wouter for routing
  └─ Tailwind CSS + shadcn/ui for styling

Layer 2: Backend (Node.js + Express + TypeScript)
  ├─ RESTful API endpoints
  ├─ WebSocket server (Socket.io)
  ├─ Middleware stack (auth, security, logging)
  ├─ Service layer pattern
  └─ Database ORM (Drizzle)

Layer 3: Database (PostgreSQL 14+)
  ├─ 120+ tables
  ├─ Complex relationships
  ├─ JSON columns for flexibility
  ├─ Indexes for performance
  └─ Backup and recovery systems

Layer 4: AI Integration Layer
  ├─ Claude 3.5 Sonnet (Anthropic)
  ├─ GPT-4o (OpenAI)
  ├─ Gemini 2.5 Pro/Flash (Google)
  ├─ Multi-model routing (87% cost reduction)
  └─ Function calling capabilities

Layer 5: Real-time Communication
  ├─ Socket.io for WebSocket connections
  ├─ User authentication per socket
  ├─ Event broadcasting
  └─ Room-based messaging

Layer 6: External Services
  ├─ Replit OAuth (authentication)
  ├─ Replit Object Storage (file uploads)
  ├─ Stripe (payments)
  ├─ SendGrid (emails)
  ├─ Luma Labs (3D avatars)
  └─ Grafana Cloud (observability)

4.5 AUTHENTICATION & MIDDLEWARE
────────────────────────────────────────────────────────────────────────────
File: server/replitAuth.ts (200+ lines)

Authentication Methods:
1. Replit OAuth (primary)
   - Uses @replit/agent-identity
   - Automatic user creation
   - Maps Replit ID to database user

2. JWT Tokens (session)
   - 24-hour expiration
   - Stored in cookies (httpOnly, secure)
   - Refreshable

3. Development Bypass
   - NODE_ENV=development auto-creates admin user
   - Skip OAuth for local testing

Middleware: isAuthenticated
Purpose: Protect routes requiring authentication
Logic:
  1. Check JWT token in cookies
  2. Verify token signature
  3. Load user from database
  4. Attach req.user object
  5. Grant/deny access

Middleware: requireAdmin
Purpose: Protect admin-only routes
Logic:
  1. Check if req.user.role === 'admin' OR 'super_admin'
  2. Return 403 if unauthorized

Middleware: requireSuperAdmin
Purpose: Protect super admin routes
Logic:
  1. Check if req.user.role === 'super_admin'
  2. Return 403 if unauthorized

Security Features:
✓ Password hashing (bcrypt, 10 rounds)
✓ CSRF protection
✓ Rate limiting (100 requests/15 minutes)
✓ Input sanitization
✓ SQL injection prevention (parameterized queries)
✓ XSS prevention (DOMPurify)

Flow:

4. Server verifies token

Timeout:

Implementation:

  try {
    const user = await verifyJWT(token)
    socket.data.userId = user.id
    socket.data.authenticated = true
    socket.join(`user:${user.id}`)
    socket.emit('authenticated', { success: true })
  } catch (error) {
    socket.emit('auth_error', { message: 'Invalid token' })

10.7 STREAMING RESPONSES (SSE)

Server-Sent Events for progressive rendering

Backend (Express):
app.post('/api/mrblue/stream', async (req, res) => {
  res.setHeader('Content-Type', 'text/event-stream')
  res.setHeader('Cache-Control', 'no-cache')
  res.setHeader('Connection', 'keep-alive')
  
  const stream = await openai.chat.completions.create({
    model: 'gpt-4o',
    messages: req.body.messages,
    stream: true
  })
  
  for await (const chunk of stream) {
    const content = chunk.choices[0]?.delta?.content || ''
    if (content) {
      res.write(`data: ${JSON.stringify({ content })}\n\n`)
    }
  }
  
  res.write('data: [DONE]\n\n')
  res.end()
})

Frontend:
const response = await fetch('/api/mrblue/stream', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ messages })
})

const reader = response.body.getReader()
const decoder = new TextDecoder()

while (true) {
  const { done, value } = await reader.read()
  if (done) break
  
  const chunk = decoder.decode(value)
  const lines = chunk.split('\n\n')
  
  for (const line of lines) {
    if (line.startsWith('data: ')) {
      const data = JSON.parse(line.slice(6))
      if (data.content) {
        updateUI(data.content) // Progressive rendering
      }
    }
  }
}
